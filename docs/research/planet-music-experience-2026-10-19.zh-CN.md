# 星球制作与音乐玩法：调研、设计和实施方案

日期：2026-10-19。状态：完成首轮资料与代码研究；以下玩法为待试玩验证的设计。用户确认当前配乐试听通过，并明确要求优先研究星球制作与音乐专属玩法，可编辑界面延期。

## 本轮边界

- 用户结果：明确星球怎样制作、玩家玩什么、音乐怎样参与，并形成可以逐项开工的方案。
- 阶段门槛：Phase 3 当前作品的体验质量，以及降低定制作品制作成本的前置验证；不宣称完成辅助生成阶段。
- 最小闭环：一段歌曲的线索 → 玩家探索和操作 → 场景发生可辨认的变化 → 乐句处汇成回应 → 重播可以恢复。
- 范围外：通用编辑器、多人、战斗、自动生成整颗星球、新引擎、发布服务、付费生成。
- 验收证据：制作流程决策、具体任务卡、音乐编排草案、逐步试玩门槛。实现后的运行证据另记。
- 性能/无障碍/权利：复用现有授权素材；不以快速按键或听觉作为唯一条件；沿用性能预算与资产审核。

## 1. 当前体验的实际缺口

代码核对：`coastalStudy.ts` 仍从 Memory Journey 创建；`childhoodScore.ts` 把原有七个事件移到 0/22/44/64/88.2/96/124.5 秒。颜色、文案和时间已为歌曲调整，核心动作仍是交谈、收取记忆、离场。

`PlayerController.tsx` 普通移动速度 5 m/s，奔跑 7.5 m/s。现有主要交互集中在出生点前方十几米内。少量移动和面板点击之后，可操作内容很快耗尽；等待门开会放大空白。

`CoastalScenery.tsx` 将布景整体设为固定三角网格碰撞，并关闭其镜头遮挡标记。增加布局范围前，需要重新检查穿景、相机遮挡和地物边缘卡住的问题。

`planetSurface.ts` 已有球面位置、法线、朝向和弧长；当前坐标是从出生点展开的局部距离。反向映射在对跖点附近有歧义。完整环星球制作需要分区或单位球法线定位的单独验证；首个玩法样片限制在局部区域。

结论：优先补探索动机、操作变化和路线节奏。布景编辑界面的收益排在玩法验证之后。

## 2. 研究结果与选型

### 参考的证据边界

Messenger 作者 Vicente Lucendo 的访谈确认 Blender/Houdini 建模、Three.js 运行与定制控制、镜头、着色。他们强调可绕行的小星球、统一轮廓与颜色，以及自动居中帮助新手；也反思应更早考虑故事。[作者访谈](https://www.commarts.com/webpicks/messenger)

本轮重新打开参考站，保留入口截图于 `output/playwright/messenger-research-2026-10-19.png` 等文件。该次浏览未完成任务链；既有人工观察见 `echo-garden-study.md`。不将外观推测写成其内部实现。

| 路线 | 能解决什么 | 代价/限制 | 本项目决定 |
|---|---|---|---|
| 固定球体 + 人工设计街区 + 程序化装饰 | 路线、构图、音乐事件可控，可复用当前物理 | 需要主动设计地标、遮挡和节奏 | 首选 |
| Blender Geometry Nodes 辅助布景 | 用表面法线、间距和固定种子分布植被 | 导出后节点逻辑不能直接成为网页玩法；交互道具需独立 | 离线制作工具，先验证一小块街区 |
| 噪声地形、动态地形/LOD | 大规模自然星球 | 地表采样、径向碰撞、导航与相机成本高，当前路线密度收益更直接 | 延后 |
| AI 一次生成整场景 | 快速得到视觉候选 | 道路可达性、资产权利、碰撞、音乐机关难以保证 | 维持候选审核，暂不采用 |

Geometry Nodes 的表面布点可以输出法线和旋转、控制最小间距与种子，用于避开主路后散布草木；关键道具与视线走廊采用人工布局。[Blender 官方文档](https://docs.blender.org/manual/id/4.3/modeling/geometry_nodes/point/distribute_points_on_faces.html)

相同网格/材质的重复物件适合实例渲染；按街区分组，减少绘制调用并保留局部剔除。GLB 优化可沿用现有 glTF Transform 的 dedup、instance、join、meshopt；交互物件禁止无差别 join，以免失去动作节点。[Three.js](https://threejs.org/docs/pages/InstancedMesh.html)、[glTF Transform](https://gltf-transform.dev/cli)

视觉模型与碰撞模型分开：树叶、花草无碰撞，树干/墙体用简单形状，复杂静态地形才用简化 trimesh；移动物件用凸体。Rapier 支持这些类型，并提示动态 trimesh 的穿入/卡住风险。[Rapier](https://rapier.rs/docs/user_guides/javascript/colliders/)

灯光先采用一盏主要阴影灯、环境补光和少量烘焙接触阴影；扩大场景时重新控制阴影覆盖。每盏阴影灯都会增加场景绘制，不能靠增加灯数堆精细度。[Three.js 阴影说明](https://threejs.org/manual/pages/shadows.html)

### 音乐参与的选择

| 方案 | 所需素材/工作 | 适用性 |
|---|---|---|
| 整曲播放 + 作者标注乐句 + 玩家动作改变世界 | 当前完整混音、少量人工标记与状态规则 | 本轮采用 |
| 多轨音乐随玩法增减声部 | 作曲分轨、同步混音和独立试听 | 当前来源页只提供完整混音，先延期 |
| 分段重组/循环等玩家完成 | 可无缝衔接的切点与过渡编曲 | 当前歌曲先保持完整聆听；不强行裁切 |
| 严格节拍判定 | 精确节拍图、输入/输出延迟校准 | 当前舒缓探索暂不采用 |

Wwise 官方资料区分分层音乐、片段/转场及游戏状态触发，可借鉴编排方法；本轮沿用现有播放器，无需引入 Wwise。[互动音乐结构](https://www.audiokinetic.com/en/public-library/2024.1.8_8893/?id=creating_interactive_music&source=Help)

《Journey》制作访谈提到围绕音乐迭代关卡原型。对本项目的推论是：先把音乐段落、路线和动作放在同一张设计表内，再做精美布景。[USC 对作曲过程的报道](https://music.usc.edu/austin-wintory-details-artistic-process-behind-journey-score-in-new-video/)

## 3. 星球制作的可执行流程

1. **音乐与体验简表**：记录情绪、音色、乐句变化、一个核心动作和结尾意义。产物为按秒编排表；RMS 只辅助定位，不能识别叙事或证明乐句。
2. **路线白盒**：沿用 60 m 球体，画入口、三个地点、可选绕路和回望点。用简单模型实际跑通，每段记录移动、观察、操作用时。首轮局部样片路径约 30–45 m；整曲路线长度由试玩决定，首个候选环路 140–180 m，避免仅拉长路程。
3. **场景结构**：地表/主路、建筑树木、动态机关、碰撞代理、镜头锚点分层。用已有球面函数统一放置和朝向。路面和碰撞共享同一份布局来源，禁止两边手调。
4. **资产套件**：先做一个精细街角与一个互动道具，确定人物尺度、色板、轮廓粗细、接触阴影和材质，再扩展。可使用 Blender 制作源文件，现有脚本负责确定性布局、命名及导出；记录工具版本与构建参数。首次 Blender 导出须单独验证变换、材质、动画与单位，不假定节点效果完整保留。
5. **场景装配**：每个互动道具有稳定 ID、原点、动作节点与碰撞代理；装饰按区域实例化。为相机留走廊，为机关留操作空间。首轮不修改整颗星球半径。
6. **编排与表演**：用歌曲时间求场景相位，用交互状态求玩家成果。机关动作、人物朝向和镜头优先服务玩家当前操作；切镜前处理遮挡，减少动态效果模式采用稳定视角。
7. **优化与验收**：授权/资产校验 → 优化构建 → 对比处理前后画面 → 完整步行碰撞检查 → 时间跳转/重播 → 支持设备性能。先保留可运行白盒作回退。

每个街区交付物：源文件、GLB、简化碰撞、布局数据、镜头锚点、音乐事件引用、权利记录、固定视角截图、性能记录。这里的结构化制作服务于开发迭代；用户编辑面板继续延期。

## 4. 《Childhood》专属玩法提案：把夏天带回来

原作者描述是钢琴与弦乐、童年感；当前片长 137.079 秒，来源页没有替代混音。[曲目原页](https://www.scottbuckley.com.au/library/childhood/)

玩家走入沉寂的花园，让三个童年场景重新活动。三个地点分别提供“发现线索、操作机关、改变路线”的不同体验。场景恢复后一直可见，最后回望能认出自己的行动。这个主题是设计提案，尚未经过用户玩法验收。

| 候选时间窗 | 玩家做什么 | 世界怎样回应 | 音乐关系与恢复 |
|---|---|---|---|
| 0–22 s | 看见飘走的纸风车，靠近并拾起；可直接开始探索 | 主角拿起风车，远处一个地点转动回应 | 入口用动作示范；文字最多一行 |
| 22–44 s | 沿运动线索找到花圃，转动风车到一个清晰朝向 | 连续花瓣指向下个地点，显出小径 | 操作有即时反馈，群体展开落在确认后的乐句标记 |
| 44–64 s | 到溪边，推动卡住的水车到止点 | 水车持续转动，踏板铺出可走捷径 | 采用一次持续操作，目标 3–5 秒；键盘可切换式操作 |
| 64–88.2 s | 沿捷径找到树下空位，放下风车 | 秋千/树影恢复活动，远处的三个场景互相回应 | 给观察与回望留空间，删掉“读面板领取”的旧动作 |
| 88.2–124.5 s | 自选回到拱门或沿高处短路回望 | 已完成的地点依次形成回声，变化由玩家成果决定 | 不要求所有人卡在同一秒同一地点；缺失地点可补做 |
| 124.5–137.079 s | 留下风车，回望花园或继续散步 | 保留成果，简短结尾和重走选项 | 无强制倒计时；音乐结束仍能完成 |

这些时间是现有 cue 的候选窗口，尚未证明是乐句/乐器进入点。下一轮逐段重听，标注少量准确的回应点和说明，避免将机械能量峰直接当音乐叙事。严禁把上表写成已完成玩法。

### 为什么会更有可玩性

每个地点都包含可读线索、玩家动作和持续的场景变化；水车还改变实际通路。玩家选择先去哪里、是否走捷径、何时回望。可选路只增加发现，不增加必须清单。首轮最多三个主互动，不加入战斗、背包或复杂分支任务。

三个机关全可补做，不用音乐时刻作为唯一入口。音乐控制世界呼吸、回应编排与情绪；玩家动作决定哪些地方被唤醒。静止等待开门的旧规则在新样片中移除，完成条件改为可解释的玩家成果；具体结尾规则随 M1 试玩确定。

### 音乐和行动的状态约定

- 音乐时间是场景编排唯一时钟；动作给即时非声音确认，群体表演可等待下一个作者标注点，建议等待不超过 1.5 秒，超出则立即回应。此数值是待测体验目标。
- 暂停/卡顿：音乐相位冻结，操作仍有状态提示；暂停期间完成的机关先保存成果，恢复后按当前相位展示，不补放过时的整段表演。
- seek：重算音乐相位，保留本次玩家成果，不伪造拾取。回退不重复发奖励，前跳不补发声音队列。
- 新样片完成时刻已错过：展示稳定完成态和短反馈，仍可走到结尾；无须重新听整首。
- 自然结束：保留探索和所有机关；Restart/换曲/换世界清空本次成果和排队回应。新样片只绑定当前曲目，换曲回到通用模板或显示明确提示，避免冒充自动定制。
- 音频延迟另测；Web Audio 输出时间戳可用于诊断，不能直接拿 AudioContext 时间当曲目进度。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/getOutputTimestamp)

## 5. 可以直接开工的任务卡

所有步骤在独立项目草稿中保留当前 demo。先 M1，通过试玩再逐步进入 M2/M3；工程验证不能替代“好不好玩”。

| 任务 | 具体交付与落点 | 通过条件 | 不通过时 |
|---|---|---|---|
| M0 编排准备 | 逐段试听；在本文件旁记录乐句标记、音色/动作理由；白盒路线图与用时 | 标记有可听依据，明确一段约 30–45 秒的试验范围 | 调整动作与窗口，不扩场景 |
| M1 首个可玩街角 | 花圃风车：寻找 → 操作 → 花瓣显路 → 玩家走过。原型资产和简单碰撞；新项目工厂放 `src/project/`；小型纯状态逻辑放 `src/interaction/` | 全程可用普通移动/E完成；关掉声音也有线索；完成后道路和场景有持续变化；早到/晚到/漏做都可恢复 | 先修操作、线索、反馈，暂停精美资产与第二机关 |
| M2 星球路线技术样片 | 同一局部区域加入溪边水车与回望点；碰撞与镜头代理分离，区域实例布景 | 走路/奔跑/折返不被边缘卡住，建筑不挡住主要操作；自由移动可见球面曲率和不同地标 | 调整路径、体量、相机；保持 60 m 半径 |
| M3 整曲定制 | 三种动作连成全曲；新编排与现有 Childhood 分开；明确完成、错过和余音处理 | 全曲有主动操作和观察；快/普通/慢三种路线都能结束，无必须空等的门 | 缩减机关或重排路线；保留现有曲长 |
| M4 美术与体验收口 | 优先精修互动道具、人物动作、前中远景和三个关键镜头；完整浏览器和性能记录 | 初见玩家能解释目标和自己的作用；画面、手感、音画关系分别验收 | 按证据修最弱环节，继续延期编辑面板 |

M1 技术任务拆分：

1. 定义最小显式状态：未发现/可操作/已唤醒、最近动作时间、已处理音乐回应点；沿用现有条件/标记内核，检查是否足够表达，不再增加 console-only 自定义动作。
2. 只在必要时给 `MusicWorldProject`、JSON Schema 和校验器增补有类型的机关配置。新增字段保持旧项目有效，导出/导入保留配置。实际字段在实现前确定。
3. `InteractionDispatcher` 接操作，纯 reducer 计算成果；世界组件消费结果。`MusicEnvironmentController` 与当前音乐 runtime 提供相位；不要在组件中另起独立歌曲计时。
4. 对 `PlayerController` 与 `CameraRig` 做最小集成；主动操作期间的移动限制须可取消、失焦释放、可恢复。
5. 自动测试覆盖非法顺序、重复操作、seek、暂停、重走；浏览器覆盖真实 E 键、实际移动通过道路、自然结束后补做。直接调用测试入口只能补充，不能代替实际游玩。

## 6. 试玩与制作质量门槛

- 每次交付先给可玩链接和一段实际操作证据，再说明修改点。M1 的目标是检验动作是否有趣，精美度暂沿用当前美术。
- 首轮邀请 3 位初见体验者作方向性观察：能否在 30 秒内理解并开始动作、是否需要口头解释、能否说出自己改变了什么、是否感觉音乐与变化有关。样本小，只支持迭代，不支持普遍满意度结论。
- 记录移动/主动操作/观察/被迫等待时间；特别标记无新信息的空等，目标避免单次超过 10 秒。慢走用户不受倒计时惩罚。
- 比较有声/静音体验，确认线索可见；减少动态效果模式保持可辨认的完成反馈，无镜头抖动和闪烁。
- 支持设备沿用 `browser-performance-budget.md`：55 FPS 中位目标、30 FPS 持续硬底线；音乐事件响应目标 ≤50 ms；150 draw calls/500k 可见三角形目标。必须在生产构建、指定设备上测量。
- 运行 `npm test`、`npm run lint`、`npm run build`；有资产更改再做资产校验、构建与感知检查；Chrome/Edge 覆盖首轮、跳转、重走、自然结束与失败恢复。

## 7. 当前决定与尚待验证

当前优先级：音乐专属玩法与星球制作样片 → 完整体验和美术验收 → 总结可复用的制作流程 → 创作者编辑界面。

已完成的是研究、设计和任务拆分。尚待验证的是三个机关是否有趣、候选时间窗是否适合、路线长度、Blender 导出细节及目标设备表现。当前 2:17 曲长适合本轮原型；3–5 分钟产品目标保留，不通过循环填时长。
